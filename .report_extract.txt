1.0  Introduction 
 
1.1  Background of the Proposed System 
The management of maintenance services in student hostel facilities has traditionally relied on 
manual, paper-based reporting processes. Students experiencing issues such as faulty electrical 
equipment, leaking water pipes, or broken furniture are required to report these problems 
verbally or through handwritten forms submitted to hostel administrators. These conventional 
methods are inherently inefficient, prone to human error, and lack the transparency and 
traceability required for effective service management. 
 
In many educational institutions, hostel maintenance requests are processed on an informal, 
first-come, first-served basis with no structured priority system. This results in critical issues, 
such as electrical hazards or water leaks, being handled with the same level of urgency as minor 
cosmetic defects. Furthermore, the absence of a centralised digital record system means that 
maintenance history is rarely documented, preventing administrators from analysing recurring 
issues or evaluating staff performance. 
 
The Student Hostel Maintenance Request & Tracking System software is developed as a 
desktop application based on Java programming language, following the principles of Object 
Oriented Programming (OOP). In the final version, the application offers an interface, which 
was designed using Java Swing libraries, and is backed by MySQL database, which stores the 
users’ credentials, as well as requests for maintenance. It implements the entire process of 
handling the maintenance requests from the moment when students submit their requests until 
their resolution and finalization supervised by the Hostel Admin (Maintenance Manager).

1.2  Problem Faced by Students and Users 
The following critical problems have been identified with the existing manual hostel 
maintenance system: 
 
• 
Maintenance requests are frequently lost, forgotten, or misplaced due to the absence 
of a formal digital logging mechanism, resulting in issues remaining unresolved 
indefinitely. 
• 
There is no structured tracking system, making it impossible for students to monitor 
the status or progress of their submitted maintenance requests. 
• 
The lack of a priority classification system results in urgent and safety-critical issues 
being handled with the same urgency as non-urgent, low-impact requests. 
• 
Inefficient and disorganised staff deployment leads to duplicated effort or unattended 
requests, reducing overall service quality and increasing resolution time. 
• 
The absence of a maintenance history log prevents the administration from identifying 
recurring problems, evaluating staff performance, or planning preventive maintenance 
activities. 
• 
Communication between students and maintenance staff is poor, leaving students 
uninformed about the progress or expected resolution timeline of their reported issues.

1.3  Objectives of the System 
The Student Hostel Maintenance Request & Tracking System is developed with the following 
general and specific objectives: 
 
General Objective: 
To design and develop a Student Hostel Maintenance Request & Tracking System using 
Object-Oriented Programming principles in Java that automates and streamlines the 
maintenance request management process within a student hostel environment. 
 
Specific Objectives: 
• 
Designing and developing a system whereby students will be able to submit 
maintenance requests through the internet by providing details such as request type 
(electrical, plumbing, or furniture), place of the problem, problem description, and 
request priority. 
• 
Designing and developing a system whereby the maintenance staff will be able to 
view their assigned requests and change the status of the request during the entire 
process of maintenance (submitted, under progress, completed, cancelled). 
• 
Designing and developing a system whereby the Hostel Admin/Maintenance Manager 
will be able to assign maintenance requests to staff members, manage ongoing 
maintenance requests, view all the requests made and their histories as well as 
monitor the general maintenance processes from his dashboard. 
• 
Integrating security features to the system such as authentication and authorization 
which include login for users, user registration, password resetting, and user roles for 
students, maintenance staff and maintenance manager. 
• 
Incorporation of main Object Oriented Programming techniques that include 
inheritance, encapsulation, abstraction, polymorphism, composition, aggregation, and 
interface. 
• 
Integration of factory design pattern by implementing MaintenanceFactory class used 
for creation of request objects. 
• 
Designing and development of a GUI with database implementation through MySQL 
database engine. 
• 
Implementation of request history using the RequestHistory class for accountability 
and analysis.

2.0  System Description 
 
2.1  Purpose of the System 
The Student Hostel Maintenance Request & Tracking System is a Java-based desktop 
application designed to digitise and automate the maintenance request management process 
within a student hostel environment. The system serves as a centralised platform that facilitates 
the seamless submission, tracking, assignment, and resolution of maintenance requests across 
three distinct categories: electrical, plumbing, and furniture. 
 
In using an organized digital system for submitting the maintenance requests rather than the 
informal method that students use, the intention is to ensure that the requests cannot be lost and 
will have faster response times, follow a priority system, and also ensure that there is a history 
recorded of all maintenance done before. The software will manage the entire life cycle of the 
request right from the point the request is made by a student, until it is assigned and handled 
by a manager and finally completed or canceled, and the details recorded in the MySQL 
database.

2.2  Target Users 
The system is designed to serve three distinct user roles within the hostel management 
structure: 
 
a) Students 
The system’s main end-users are the students who reside in the hostel. When registering, a 
student is assigned a room number based on the student account. Once logged in, students can 
request new maintenance by selecting the type of request. Then, they enter the name of the 
place where the problem occurred, provide a description of the issue and set a priority. The 
dashboard displays a student’s active requests and allows them to search the complete history 
of all their previously-submitted requests (including current status and priority); no need to 
manually follow up with staff. 
 
b) Maintenance Staff 
Maintenance team members carry out their responsibilities on the basis of assigned requests 
submitted to the team by its manager. The system provides a user with a personalized dashboard 
page where they can see their profile, list of in-progress requests and completed and cancelled 
requests. The maintenance member can change the status of requests they are working on by 
marking them as Completed or Cancelled. From the page, he or she also may check room 
details and details of a student who submitted the request. The request history shows all 
requests that have been submitted, cancelled or completed. 
 
c) Maintenance Manager 
The Hostel Admin is the system administrator and the superintendent of all maintenance 
operations. The manager account is pre-seeded in the database and cannot be created through 
public registration. Once logged in, the manager can see dashboard statistics such as total, 
active, completed and cancelled requests, manage active in-progress requests, assign 
unassigned submitted requests to available staff members, see room details associated with a 
request and view the full request history with search and filter options.

2.3  Main Features and Functionalities 
The system provides the following key features and functionalities: 
 
• 
User Authentication and Registration: The system provides a login page for all user 
roles. New Student and Staff accounts can be registered through a sign-up form. Users 
who forget their password can verify their registered email and set a new password. 
Upon successful login, users are redirected to a role-specific dashboard. 
• 
Maintenance Request Submission: Students submit maintenance requests 
electronically by selecting the request category (electrical, plumbing, or furniture), 
confirming their room number, entering the place name, providing a detailed issue 
description, and selecting a priority level (High, Medium, or Low). 
• 
Priority-Based Request Management: Each maintenance request is assigned a 
priority level, ensuring that critical or safety-related issues can be identified and 
handled appropriately. 
• 
Request Status Tracking: The system maintains and displays the lifecycle status of 
every request using the Status enumeration: SUBMITTED, IN_PROGRESS, 
COMPLETED, and CANCELLED, giving all users clear visibility of the current state 
of each request. 
• 
Staff Assignment: The Hostel Admin assigns specific staff members to submitted 
requests that have not yet been assigned. Once assigned, the request status is 
automatically updated to IN_PROGRESS. 
• 
Request History Logging: All status changes for a given request are recorded by the 
RequestHistory class in memory and persisted in the database, providing a complete 
audit trail from submission to resolution. 
• 
Search and Filter Functionality: Students, staff, and the manager can search and 
filter request records by request ID, status, type, or priority depending on their role, 
enabling efficient retrieval of specific records. 
• 
Factory-Based Request Creation: The MaintenanceFactory class dynamically 
instantiates the appropriate request subclass (ElectricalRequest, PlumbingRequest, or 
FurnitureRequest) based on the request type provided, implementing the Factory 
Design Pattern to decouple object creation from client code. 
• 
Database Persistence: All user and request data is persisted through the 
DatabaseHandler class, which implements the DataAccess interface and provides

3.4    Explanation of Relationships 
The classes within the system interact through several well-defined Object-Oriented 
relationships. These relationships are visually represented in the UML Class Diagram and are 
explained in detail below. 
 
3.4.1  Inheritance 
Inheritance establishes an "is-a" relationship between a parent (superclass) and its child classes 
(subclasses), promoting code reuse and establishing a clear class hierarchy. 
 
• User → Student, Staff, and HostelAdmin: All three user types inherit from the 
abstract User class. They reuse common attributes and provide concrete 
implementations of login() and logout(). 
• 
MaintenanceRequest → ElectricalRequest, PlumbingRequest, and FurnitureRequest: 
All three concrete request types inherit from MaintenanceRequest. They inherit core 
request attributes and override the abstract processRequest() method with type-
specific logic, demonstrating polymorphism. 
 
3.4.2  Realization (Interface Implementation) 
Realization represents a "implements" relationship, shown as a dashed line with a hollow 
triangle pointing to the interface.  
 
• 
User → Authenticatable: The User class implements the Authenticatable interface, 
providing concrete implementations of getEmail(), checkPassword(), and getRole(). 
• 
DatabaseHandler → DataAccess: The DatabaseHandler class implements the 
DataAccess interface, providing all persistent database operations defined in the 
contract.

3.4.3  Composition 
Composition represents a strong "has-a" relationship (filled diamond), where the contained 
object's lifecycle depends on the container. 
 
• Student ◆→ MaintenanceRequest (1 to 0..*): A Student owns a list of 
MaintenanceRequest objects submitted through their account. These requests are 
created as part of the student's interaction with the system. 
• 
MaintenanceRequest ◆→ RequestHistory (1 to 1): Each MaintenanceRequest 
contains exactly one RequestHistory object, created automatically when the request is 
instantiated. The history cannot exist independently of its parent request. 
 
3.4.4  Aggregation 
Aggregation represents a weak "has-a" relationship (hollow diamond), where the contained 
object can exist independently of the container. 
 
• Staff ◇→ MaintenanceRequest (1 to 0..*): A Staff member holds a list of assigned 
MaintenanceRequest objects. Requests exist independently in the system and can be 
reassigned to a different staff member. 
• MaintenanceManager ◇→ MaintenanceRequest (1 to 0..*): The 
MaintenanceManager maintains an in-memory collection of all MaintenanceRequest 
objects loaded from the database. 
• 
Room ◇→ MaintenanceRequest (1 to 0..*): A Room maintains a list of linked 
MaintenanceRequest objects. Requests exist independently and can be associated with 
different rooms.

3.4.5  Association 
Association represents a general reference relationship between two classes without implying 
ownership. 
 
• User → UserRole (1 to 1): Each User has exactly one UserRole (STUDENT, STAFF, 
or MANAGER) stored in the role attribute. 
• Student → Room (1 to 0..1): Each Student is associated with one Room object linked 
to their account at registration. 
• MaintenanceRequest → Room (0.. to 1):* Each MaintenanceRequest is associated 
with exactly one Room, providing the physical location of the reported issue. 
• MaintenanceRequest → Status (1 to 1): Each MaintenanceRequest has exactly one 
current Status value. 
• 
SessionManager → User (1 to 0..1): The SessionManager holds a reference to the 
currently logged-in User for the active session. 
 
3.4.6  Dependency 
Dependency represents a "uses" relationship (dashed arrow), where one class depends on 
another without a permanent structural link. 
 
• 
MaintenanceFactory <> MaintenanceRequest: The factory dynamically creates 
concrete request subclasses at runtime based on the request type. 
• 
DatabaseHandler <> MaintenanceFactory: DatabaseHandler uses MaintenanceFactory 
to reconstruct request objects when loading data from the database. 
• 
AuthService, StudentService, StaffService, ManagerService <> DataAccess: All 
service classes depend on the DataAccess interface (implemented by 
DatabaseHandler) to perform database operations. 
• 
AuthService <> SessionManager and SignUpData: AuthService uses SessionManager 
to store the logged-in user and SignUpData as the registration payload. 
• 
StudentService <> MaintenanceFactory and MaintenanceManager: StudentService 
uses the factory to create new requests and the manager to update the in-memory 
request list after submission.

4.0  System Design 
 
4.1  Programming Language and Development Environment 
The Student Hostel Maintenance Request & Tracking System was developed using Java in 
NetBeans IDE, as required by the project guideline. The system was built in two phases: 
 
• Phase II (Console Application): The Main class provides a text-based menu for 
submitting, searching, updating, and tracking maintenance requests through the IDE 
console. 
• Phase III (Enhanced Application): The system was extended with a Graphical User 
Interface (GUI) using Java Swing, MySQL database integration via JDBC, and 
advanced OOP features including abstract classes, interfaces, polymorphism, and the 
Factory Design Pattern. 
• The backend database runs on XAMPP MySQL using the schema defined in 
hostel_maintenance_schema.sql. Database connection settings are centralized in the 
DatabaseConfig class, while all SQL operations are handled through the 
DatabaseHandler class, which implements the DataAccess interface.

4.2.2 Maintenance Request Hierarchy 
MaintenanceRequest is an abstract class representing any hostel maintenance issue. It contains 
encapsulated fields such as requestId, description, priority, status, room, and dateRaised. Each 
request is automatically linked to a RequestHistory object upon creation.

4.2.3  Factory Design Pattern – MaintenanceFactory 
The Factory Design Pattern is applied through the MaintenanceFactory class. Instead of 
creating request objects directly throughout the system, the factory centralizes object creation 
based on request type. 
 
The method createRequest(String type, String requestId, String description, String priority, 
Room room) uses a switch statement to instantiate the correct subclass: 
 
• "electrical" → ElectricalRequest 
• "plumbing" → PlumbingRequest 
• "furniture" → FurnitureRequest 
 
This pattern improves code reusability and maintainability, because adding a new request type 
only requires updating the factory class rather than every part of the system that creates 
requests.

4.2.4  Room and Request History 
The Room class represents a hostel room using roomNumber and placeName. It maintains an 
array of linked maintenance requests, demonstrating aggregation — a room can exist 
independently, but it references multiple requests. 
 
The RequestHistory class tracks all status changes for a single request. It is created inside the 
MaintenanceRequest constructor, forming a composition relationship — the history cannot 
exist without its parent request. Key methods include: 
 
• recordStatus(Status newStatus) — logs each status change using a String[] history log 
and int[] status counters 
• viewHistory() — displays the full change log and status summary

4.2.6  Database Layer – DataAccess Interface and DatabaseHandler 
The DataAccess interface defines the contract for all database operations, including: 
 
• Create: registerStudent(), registerStaff(), insertRequest(), findOrCreateRoom() 
• Read: authenticate(), findRequestById(), fetchAllRequests(), 
fetchRequestsByStudent(), fetchRequestsByStaff(), fetchAllStaff() 
• Update: updateRequestStatus(), assignStaffToRequest(), updatePassword() 
• Delete: deleteRequest() 
 
The DatabaseHandler class implements DataAccess using the Singleton pattern (getInstance()), 
ensuring only one database connection handler exists. It uses JDBC with PreparedStatement to 
prevent SQL injection and executes SQL queries against four main tables: users, rooms, 
maintenance_requests, and request_status_history. 
 
When loading requests from the database, DatabaseHandler uses MaintenanceFactory to 
recreate the correct MaintenanceRequest subclass based on the stored request_type, again 
demonstrating polymorphism.

6.1  Project Summary 
The Student Hostel Maintenance Request & Tracking System is a group project developed for 
the course BCS2143 Object-Oriented Programming.  
The main issue is about student hostel maintenance requesting and tracking. It is a system for 
students, staff and managers to perform different functionalities on a new digital platform. 
  
The project was developed in phases where in Phase II a console application was created and 
then in Phase III it was enhanced to a fully functional GUI application with MySQL database 
integration. The system displays the application of basic OOP concepts such as encapsulation, 
abstraction, inheritance, polymorphism, composition, aggregation, interfaces and the Factory 
Design Pattern in an actual scenario that pertains to student life on a campus.

6.2  What the Group Learned from the Project 
Through this project, the group gained valuable knowledge and hands-on experience in both 
software development and teamwork: 
 
Object-Oriented Programming Concepts 
The group learned how to translate theoretical OOP concepts into a working application. For 
example, inheritance was applied through the User and MaintenanceRequest class hierarchies, 
while polymorphism was demonstrated through overridden methods such as login(), logout(), 
and processRequest(). The Factory Design Pattern taught the group how to centralize object 
creation and improve code maintainability. Composition and aggregation were understood in 
practice — RequestHistory is composed within each MaintenanceRequest, while Room and 
MaintenanceManager aggregate collections of requests. 
 
System Design and Architecture 
The group learned to design a system using UML class diagrams before implementation, and 
to organize code into logical layers: Model, Data Access, Service, and Presentation. This 
separation made the codebase easier to manage, debug, and extend as new features were added 
during Phase III. 
 
Database Integration 
Integrating MySQL through JDBC exposed the group to real database operations. The 
DatabaseHandler class implements full CRUD functionality — creating user accounts and 
requests, reading and searching records, updating statuses and assignments, and deleting 
requests when needed. The group also learned the importance of using PreparedStatement to 
write secure SQL queries and of designing relational tables with foreign keys to maintain data 
integrity. 
 
Graphical User Interface Development 
Building the GUI with Java Swing required the group to think about user experience, not just 
functionality. Role-based dashboards were designed so that each user type sees only relevant 
features. Form validation, error messages, and success confirmations were implemented to 
guide users and prevent invalid input.

Software Development Practices 
The group learned the value of working in phases, backing up code regularly, and testing each

helped keep development consistent across team members. Clear naming conventions, 
encapsulation, and reusable components (such as those in the gui.common package) improved 
code readability and reduced duplication. 
 
Teamwork and Individual Responsibility 
As a group project, each member contributed to different modules — domain classes, database 
layer, authentication, student/staff/manager GUI screens, and documentation. The group 
learned to coordinate tasks, integrate individual contributions into a single cohesive system,

on expertise (e.g. Electrician, Plumber). 
• Request history and room details are accessible in one system, improving oversight
